Deep jumps in the LinearLite list at 100k issues: which design makes the first jump to row 50,000 cheap.
Machine, Chrome and server as in client-100k-prod.txt (the server a fresh `pnpm seed 100000`). Production builds,
one profile per build filled by one first sync, warm and offline. One run per build per round, the build order
rotated each round, each run under the machine-wide lock; p50 (min-max) over 5 runs.

base  PR 179's head (cec65c9): one live query from the top of the order. TanStack loads a window at offset N as
      the first N rows plus the window (`loadPrefix`), the adapter reads every one of them, and they stay.
A     base plus a TanStack index on issues (`autoIndex: "eager", defaultIndexType: BTreeIndex`). With an index on
      the order field TanStack's loader pages with a cursor and asks only for the rows it lacks.
C     base with the `byModified` reads served from an array of all 100,000 issues loaded before the timed jumps: the
      floor for keeping the prefix and making its read free.
B     this branch (a883e6e): a window deep in the unfiltered list is its own live query, anchored at the sort value
      of its row (`useIssueWindow`, `locate` in src/client/counts.ts).

A and C were throwaway builds of base, not kept; they also logged the adapter's loadSubset calls.

Why each one lost:
- A reads the same rows as base. The adapter's log of TanStack's loads: the first jump to 5,000 asks for 4,958
  rows after a cursor, the first jump to 50,000 for 45,000 more. The cursor saves TanStack re-asking for rows it
  holds, not reading the rows above the window; the BTree index over 50,058 rows costs 11 MB more.
- C shows what is left when reading the prefix costs nothing: 234 ms, TanStack taking in the 50,058 rows above
  and in the window, and keeping them, so memory stays where base is (plus C's array).
- B walks the sort index's entries down to row N without reading their documents, reads the 65 documents ending
  at it, and loads a 100-row window bounded by row N's sort value. Most of its first jump is that walk, cold
  (below). The count of the rows before the anchor runs after the rows show, and again after every change. Its
  later jumps are slower than base's (31 and 67 ms against 15): a jump from the top places a new query and walks
  the index again, where base finds the rows in memory. Its memory is the window: 700 rows after the jumps, the
  100 at the top once TanStack drops the anchored query (gcTime 5 s).
